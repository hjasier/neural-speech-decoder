Cómo trabajar en el repositorio

Guía paso a paso. Si algo no te sale, busca aquí antes de preguntar.

Parte 1 · El primer día

Esto se hace una sola vez, y solo lo hace una persona de la pareja.

1. Crear vuestro repositorio

Entra en el repositorio de la plantilla y pulsa el botón verde que dice «Use this template», y luego «Create a new repository».

Ponle un nombre, por ejemplo resnet-cifar10. Déjalo en Private. Pulsa crear.

No hagáis «clone» de la plantilla. Con «Use this template» el repositorio es vuestro y empieza limpio. Clonando os llevaríais mi historial.

2. Dar acceso a los demás

En vuestro repositorio nuevo: Settings → Collaborators → Add people.

Añadid a dos personas: tu pareja y el profesor.

Sin esto, tu compañero no puede tocar nada y yo no puedo corregir.

3. Descargarlo a vuestro ordenador

Esto lo hacéis los dos, cada uno en su ordenador.

git clone https://github.com/TU-USUARIO/TU-REPO.git
cd TU-REPO

clone significa «tráete una copia». Ahora tienes el proyecto en tu disco.

4. Preparar el entorno de Python

python -m venv .venv
source .venv/bin/activate          # en Windows: .venv\Scripts\activate
pip install -r requirements.txt

Un entorno virtual es una caja donde se instalan las librerías de este proyecto y de ningún otro. Así no se mezclan versiones entre asignaturas.

Tendrás que activarlo cada vez que abras una terminal nueva. Si ves (.venv) al principio de la línea, está activado.

5. Comprobar que funciona

python run.py --smoke
python tools/tiiac_check.py .

El primero entrena un poquito y saca dos números. El segundo te da una nota sobre 100.

Tiene que salir 88 y en VERDE. Si sale eso, ya está.

Verás dos avisos: que falta el enlace de W&B y que el AI_USAGE.md está vacío. Es normal. Son 12 puntos que iréis completando durante el curso.

6. Decirle a git quién eres

Solo la primera vez en tu ordenador:

git config --global user.name "Tu Nombre"
git config --global user.email "tu.correo@opendeusto.es"

Esto es lo que hace que cada cambio quede a nombre de quien lo hizo. Importa: es como se ve quién ha trabajado.

Parte 2 · El día a día

Este es el ciclo que vas a repetir todo el semestre. Cuatro pasos.

Paso 1 · Antes de empezar, tráete lo nuevo

git pull

Trae los cambios que haya hecho tu compañero.

Hazlo siempre. El 90 % de los líos con git salen de no hacer pull antes de ponerse.

Paso 2 · Trabaja

Escribe código. Cambia lo que tengas que cambiar.

Paso 3 · Comprueba que no has roto nada

python run.py --smoke
pytest tests/ -q

Si algo falla, arréglalo antes de subirlo. Subir código roto le hace perder tiempo a tu compañero.

Paso 4 · Guarda y sube

git add -A
git commit -m "Añade la normalización de CIFAR"
git push

Qué hace cada uno:

  • git add -A marca los ficheros que quieres guardar.
  • git commit los guarda en tu ordenador, con un mensaje.
  • git push los sube a GitHub, para que tu compañero los vea.

commit no es push. Si haces commit y no push, el cambio sigue solo en tu ordenador. Es el error más común.

Y luego, mira el semáforo

Entra en tu repositorio en GitHub, pestaña Actions. Verás una marca:

  • Verde: tu código funciona también en un ordenador limpio.
  • Rojo: funciona en el tuyo pero no en otro. Pincha y mira qué dice.

Parte 3 · Mensajes de commit

Un buen mensaje se entiende dentro de tres meses. Tres reglas:

Uno por idea. Si el mensaje necesita un «y», son dos commits.

Empieza con un verbo. «Añade», «Corrige», «Elimina».

Di el porqué si no es evidente.

Malos:

cambios
mas cambios
ahora si
Update train.py

Buenos:

Añade la normalización con las medias del paper
Corrige el orden de canales en el DataLoader
Reduce el subset a 5000 imágenes para caber en la regla 5/20

Esto se mira en la nota de E1, dentro de los 4 puntos del repositorio. Y en noviembre otra pareja va a leer vuestro historial para entender por dónde fuisteis.

Parte 4 · Tres cosas que hay que ir alimentando

Los tests, la bitácora de IA y el registro de experimentos no se hacen en diciembre. Se van llenando sobre la marcha, y valen puntos.

Si los dejáis para el final, se nota: no os vais a acordar de lo que hicisteis en octubre.

4.1 · Los tests

Los que trae la plantilla son ejemplos, y dejan de servir en cuanto cambiéis el modelo. Están escritos contra un modelo de juguete. Cuando metáis el de vuestro paper se van a romper. Es normal: hay que reescribirlos.

Cuándo escribir uno

Cuando arregles un fallo que no daba error. Esa es la regla. Si has perdido dos horas porque los datos iban mal ordenados y no saltaba ninguna excepción, escribe un test que lo habría cazado.

También cuando escribas algo que pueda romperse en silencio: formas de tensores, orden de canales, cómo se parten los datos.

Qué tipos hay

De forma. Comprueba que la salida tiene el tamaño que dice el paper.

def test_la_salida_tiene_10_clases():
    modelo = construir_modelo(CFG)
    x = torch.randn(4, 3, 32, 32)
    assert modelo(x).shape == (4, 10)

De que no se mezclan los datos. Si el modelo mezcla ejemplos entre sí, pasar cuatro imágenes juntas o de una en una tendría que dar lo mismo. Si no, hay un fallo grave.

def test_el_batch_no_se_mezcla():
    modelo = construir_modelo(CFG).eval()
    x = torch.randn(8, 3, 32, 32)
    with torch.no_grad():
        juntas = modelo(x)
        sueltas = torch.cat([modelo(x[i:i+1]) for i in range(8)])
    assert torch.allclose(juntas, sueltas, atol=1e-4)

De reproducibilidad. La misma semilla tiene que dar los mismos pesos. Si esto falla, comparar dos experimentos no significa nada.

Cómo se ejecutan

pytest tests/ -q

Tienen que pasar antes de subir código.

Cuánto hace falta

No hay que cubrirlo todo. Con las partes que pueden fallar sin avisar ya vale.

Valen 4 puntos de E2, junto con la calidad del código. Y hay media clase sobre esto el 18 de noviembre.

Si borráis los tests, la comprobación automática pasa igual: pytest sin tests no falla. Pero los puntos se pierden, y en la auditoría de noviembre otra pareja va a mirar vuestro código.

4.2 · La bitácora de IA

Es el fichero AI_USAGE.md, en la raíz del repositorio. Vale 2 puntos de E2.

Qué se apunta

Una fila cada vez que uséis una herramienta de IA para algo que acabe en el proyecto:

Fecha Qué le pedisteis Qué os devolvió Qué hicisteis con ello y por qué
14-oct «¿Por qué mi loss no baja?» Cinco posibles causas No lo usamos como diagnóstico. Nos sirvió de lista de comprobación; el fallo lo encontramos nosotros: el pooling estaba después del flatten

Cuándo se escribe

En el momento. Cuesta treinta segundos, y en diciembre no te acuerdas.

Qué se puntúa

El criterio, no la cantidad. Podéis usarla mucho y sacar los 2 puntos, o poco y sacar 0.

La entrada que mejor puntúa es la que dice «nos dio esto y lo rechazamos porque…». Demuestra que leísteis lo que os dio y que sabéis cuándo no fiaros.

Lo que no se puede pedir

Se puede usar para escribir código, entender una API o traducir el pseudocódigo del paper.

No para interpretar vuestras curvas ni para escribir la discusión de resultados. Eso es lo que evalúa la asignatura.

Y hay una razón práctica: ninguna IA ha visto vuestros datos. Lo que os diga sobre vuestros resultados se lo está inventando, y suena bien mientras lo dice.

4.3 · Weights & Biases

Es una web que guarda las curvas de vuestros entrenamientos. Sin ella, cuando hayáis entrenado veinte veces no vais a saber cuál fue cuál.

Preparación, una sola vez

1. Cread una cuenta gratis en https://wandb.ai. Con el correo de la universidad tenéis plan académico.

2. Copiad vuestra clave desde https://wandb.ai/authorize.

3. Identificaos en vuestro ordenador:

wandb login

Os pedirá la clave. Se guarda y no hay que repetirlo.

4. Poned vuestro usuario en la configuración. En configs/default.yaml:

wandb:
  proyecto: tiiac-2026
  entidad: vuestro-usuario-de-wandb
  modo: online

5. Enlazad el proyecto en el README:

- **Experimentos:** https://wandb.ai/vuestro-usuario/tiiac-2026

Ese enlace son 5 puntos del checker. Sin él os avisa de que falta, y es uno de los dos avisos que veis desde el primer día.

Cómo se usa

Nada más. run.py ya registra los entrenamientos. Cada vez que ejecutéis:

python run.py --config configs/default.yaml

aparecerá un run nuevo en la web, con sus curvas.

En el --smoke no se registra nada, a propósito: sería ruido.

Qué se mira

Que los experimentos que citáis en el informe se puedan encontrar en W&B. Si en el informe decís «con learning rate 0.01 sale 0.71», tiene que haber un run que lo enseñe.

La fecha para tenerlo funcionando es el hito H3, el 4 de octubre.

Parte 5 · Trabajar por funcionalidades

Al principio, cuando el proyecto es pequeño, trabajad los dos directamente. Ya está bien así.

Cuando el proyecto crezca, y sobre todo a partir de noviembre, conviene cambiar a este método. Lo vemos en clase el 16 de noviembre.

Qué es una funcionalidad

Una cosa concreta que quieres añadir. Por ejemplo: «meter early stopping», «añadir el mapa de calor», «hacer que se guarden los pesos».

No es «avanzar el proyecto». Eso es demasiado grande.

Los pasos

1. Crea una rama

git switch -c early-stopping

Una rama es una copia paralela donde trabajas sin molestar. Si la lías, la borras y no pasa nada.

2. Trabaja y haz commits pequeños

Igual que siempre: add, commit. Varios commits pequeños son mejor que uno gigante.

3. Súbela

git push -u origin early-stopping

4. Abre un pull request

En GitHub te aparecerá un botón amarillo que dice «Compare & pull request». Púlsalo y créalo.

Un pull request es decir: «he hecho esto, ¿lo miras antes de meterlo?».

5. Que tu compañero lo lea

Él mira el código, comenta si ve algo raro, tú corriges.

Nadie mete su propio código sin que el otro lo lea. No es burocracia: el que escribió el código ya no ve los fallos, y el que no lo escribió sí. Además evita que solo uno entienda cada parte, y en la defensa se os pregunta a los dos.

6. Júntalo y borra la rama

Cuando esté bien, pulsáis «Merge pull request» y luego «Delete branch».

Y en tu ordenador:

git switch main
git pull

Dos consejos

Ramas cortas. Dos o tres días como mucho. Una rama de dos semanas da problemas seguro.

Pull requests pequeños. Uno de 800 líneas nadie lo lee, se aprueba y ya. Uno de 80 sí se lee.

Parte 6 · Cuando algo va mal

«No me deja hacer push»

! [rejected]  main -> main (fetch first)

Significa que tu compañero subió algo y tú no lo tienes. No es un error, es git protegiéndote.

git pull
git push

Un conflicto

Si los dos habéis tocado la misma línea, al hacer pull verás:

CONFLICT (content): Merge conflict in configs/default.yaml

Abre el fichero. Verás algo así:

<<<<<<< HEAD
learning_rate: 0.0001
=======
learning_rate: 0.01
>>>>>>> a3f21b8
  • Arriba está lo tuyo.
  • Abajo está lo de tu compañero.

Git no ha perdido nada. Solo te pregunta cuál quieres.

Borra las líneas de <<<<<<<, ======= y >>>>>>>, deja el texto que queráis, y:

git add configs/default.yaml
git commit -m "Resuelve el conflicto: nos quedamos con lr 0.01"
git push

Habladlo entre vosotros antes de decidir. Un conflicto no es un problema técnico, es que los dos queríais cosas distintas.

«La he liado, quiero volver atrás»

Si aún no has hecho commit:

git restore nombre-del-fichero

Si ya lo subiste y quieres deshacerlo:

git revert EL-CODIGO-DEL-COMMIT

Nunca borréis la carpeta para volver a clonar. Es la reacción instintiva y se pierde trabajo. Todo tiene arreglo.

Parte 7 · Qué NO se sube

La regla, en una frase: al repositorio va lo que escribes tú, no lo que se genera solo.

No subas Por qué
data/ Pesa mucho y tiene licencia propia
Los pesos del modelo (.pt, .pth) Se regeneran entrenando. Y un fichero de 200 MB no se borra nunca del historial
.venv/ Se reconstruye con pip install -r requirements.txt
__pycache__/, wandb/ Son ficheros temporales
Contraseñas o claves Una clave subida está comprometida para siempre, aunque la borres después. Habría que cambiarla

El .gitignore de la plantilla ya se encarga de casi todo. Si el checker te avisa de algo de esta lista, hazle caso.

¿Y cómo consigue los datos quien clone el repositorio?

Con scripts/get_data.py. Ese script sí va al repositorio: pesa nada, descarga los datos del sitio oficial y comprueba que son los correctos.

Lo que no vale es «te lo paso por Drive». En noviembre otra pareja tiene que poder descargarse vuestros datos sola.

Parte 8 · Entregar

Entregar es poner una etiqueta en el punto exacto del historial que queréis que se corrija.

git tag -a e1 -m "Entrega E1"
git push origin e1

Y en ALUD escribís dos cosas: el nombre de la etiqueta (e1) y el código del commit, que sacáis con:

git rev-parse e1

Se corrige lo que marca la etiqueta, no lo último que haya. Podéis seguir tocando el repositorio después: eso no se mira.

Etiqueta Fecha
e1 viernes 30 de octubre, 23:59
e2 viernes 4 de diciembre, 23:59

Antes de poner la etiqueta, comprobad que el checker está en verde. Si está en rojo, la entrega no se corrige hasta que lo arregléis.

Chuleta

# empezar a trabajar
git pull

# ver cómo está la cosa
git status

# guardar y subir
git add -A
git commit -m "Un mensaje que se entienda"
git push

# comprobar antes de subir
python run.py --smoke
pytest tests/ -q
python tools/tiiac_check.py .

# ver el historial
git log --oneline

# por funcionalidades
git switch -c nombre-de-la-cosa
git push -u origin nombre-de-la-cosa

Si te pierdes, git status casi siempre te dice qué hacer. Léelo antes de buscar en internet.
